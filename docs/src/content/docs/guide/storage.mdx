Your account model belongs to your application. A subject can be a row in your
existing customer table or an identity managed by another service. Yielded Auth
needs ways to look up that identity and durably store credentials, proofs, and
sessions; core does not require an ORM or a particular database.

Choose how to provide those services:

| Start with                          | When it fits                                                             |
| ----------------------------------- | ------------------------------------------------------------------------ |
| [Managed tables](#managed-tables)   | You want auth storage supplied alongside your account table.             |
| [Your schema](#your-schema)         | You already own SQL tables and migrations.                               |
| [Your services](#your-services)     | Your backend needs a custom store or transaction model.                  |
| [In-memory tests](#in-memory-tests) | You need seeded password sign-in and stateful sessions in Node.js tests. |

Replacing storage Layers keeps your contract, `AppAuth`, and client unchanged. Moving existing data still
requires an application-owned migration.

## Managed tables

Map your account table and let Yielded Auth define the rest:

```ts title="apps/server/schema.ts"
import { Schema as AuthSchema } from "@yielded/auth";
import { AuthPersistence } from "@yielded/auth-persistence-drizzle/SqliteBun";
import { Effect } from "effect";

import { AppAuth, requirement } from "./auth";
import { customers } from "./customers";

export const Persistence = AuthPersistence.make(AppAuth);

export const storage = Persistence.managed({
  subjects: {
    table: customers,
    id: "id",
    status: "enabled",
    activeValue: true,
    securityRevision: "securityRevision",
    idCodec: AuthSchema.SubjectId,
    requirements: () => Effect.succeed(requirement),
  },
  prefix: "customer_auth",
});

export const authSchema = storage.schema;
```

Only the methods you install add tables. Export them from `authSchema` and
Drizzle Kit generates their migrations; review, commit, and apply them like any
other migration. In the example, a migration Layer applies committed files at
startup; it never pushes schema changes. You decide when migrations run.

To give a single table your own layout, pass it in `tables`. The rest stay managed.

## Your schema

Declare every table yourself, with your own names and columns:

```ts title="apps/server/tables.ts"
export const identifiers = sqliteTable(
  "app_identifiers",
  {
    moduleId: text("c_module_id"),
    credentialId: text("c_credential_id"),
    namespace: text("c_namespace").notNull(),
    value: text("c_value").notNull(),
    subjectId: text("c_subject_id").notNull(),
    revision: text("c_revision").notNull(),
    verifiedAt: integer("c_verified_at"),
    active: integer("c_active", { mode: "boolean" }).notNull(),
  },
  (table) => [uniqueIndex("app_identifiers_key_0").on(table.namespace, table.value)],
);
```

Then map them with `Persistence.map`. TypeScript requires a table for every
storage role your installed methods use:

```ts title="apps/server/schema.ts"
export const storage = Persistence.map({
  subjects: { table: customers, id: "id", status: "enabled" /* … */ },
  tables: {
    identifiers: tables.identifiers,
    credentials: tables.credentials,
    passwords: tables.passwords,
    sessions: tables.sessions,
    pending: tables.pending,
    // …one entry per role
  },
});
```

The library still runs every query and transaction. On its first storage operation,
the composed persistence Layer checks each mapped column and unique key against the
database. Cookie-cached and anonymous session reads skip this initialization.
The stateful backend supplies pending login, step-up, and bounded session cleanup
from one module-scoped pending table; each operation checks its own kind.

The same `Persistence.map` works without Drizzle. Import `AuthPersistence` from
`@yielded/auth-persistence`, describe the tables for Effect SQL, and write the DDL
yourself. The [Effect SQL app](https://github.com/yielded-dev/auth/tree/main/examples/persistence-sql)
runs on SQLite and PostgreSQL. For upstream OAuth sign-in, registration, linked
logins, and retained provider grants, use the explicit
[`OAuthPersistence` factories](../reference/adapters#oauth) from the same package.
They can map Kysely-owned tables and migrations; coordinated writes still use the
Effect SQL transaction owner.

## Your services

Each storage role is a public service, such as `Password.PasswordPersistence`.
Implement them in your own Layers. The rest of auth calls those services through
Effect, without knowing whether they use SQL:

```ts title="apps/server/live.ts"
export const PersistenceLive = Layer.mergeAll(
  PasswordsLive,
  ProofsLive,
  EmailLive,
  PasskeysLive,
  SessionsLive,
);
```

The Layers above are application implementations, not library exports. The
[custom services app](https://github.com/yielded-dev/auth/tree/main/examples/persistence-custom)
implements these boundaries with a single-writer file store and no persistence
package. It runs the account workflows with the same shared UI; its extra
username sign-in uses an extended contract.

### What a custom backend must guarantee

Storage services describe workflow commits, not just CRUD. Your implementation
must recheck the relevant account and credential state and consume proofs with
protected changes in the same commit. The commit receipt releases private
credentials and lifecycle events only after that owner succeeds. Durable replay
is available only where a workflow explicitly retains its original decision.

Choose a transaction or batch owner that can uphold those contracts. Splitting
account and credential writes across independent backends does not make them
atomic. An uncertain commit requires reconciliation, not another credential
issuance. The [adapter reference](../reference/adapters) covers the supported
transaction boundaries, including D1 and Durable Objects.

The file-store example supports one process on a local filesystem. It illustrates
the service boundary; replication and production storage operations remain yours.

## In-memory tests

Import `@yielded/auth-persistence/Testing` explicitly for tests with one
`Password.make()` sign-in strategy and `Sessions.stateful()`. It creates and seeds
a scoped SQLite `:memory:` database using the real SQL authority and session
implementations. Each acquisition starts fresh; reusing a Layer within one build
shares its state. Closing the scope discards everything. This is process-local,
non-durable test storage, never a production default.

Install the optional driver alongside the persistence package:

```sh
bun add -d @yielded/auth-persistence@beta @effect/sql-sqlite-node
```

The driver requires Node.js 24 or newer with `node:sqlite` support.
This helper is not a browser, Bun, D1, or PostgreSQL emulator. Its native dependency
is absent from core and the persistence package's production import paths.

```ts
import * as Testing from "@yielded/auth-persistence/Testing";
import { Redacted } from "effect";

const TestPersistence = Testing.layer(AppAuth, {
  subjects: [{
    subjectId: "reader",
    email: "reader@example.invalid",
    password: Redacted.make("test passphrase"),
  }],
  requirement, // Your explicit AuthenticationRequirement
  clock: "test",
});
```

Provide this Layer to `AppAuth.layer`, alongside your password strategy's
`SessionClaims`, `PasswordHashing`, and Effect `Crypto` Layers. Seed passwords are
byte-preserving and hashed with that same hasher. Email addresses are normalized;
they remain unverified. `active: false` seeds a disabled subject. Invalid seeds or
duplicate subject IDs/emails fail acquisition. Application claims, authentication
requirements, session lifetime, and private credential delivery remain explicit.

In `it.effect`, use `clock: "test"` and call `Testing.syncClock` after each
`TestClock.adjust` or `setTime`, between auth operations. SQL and auth then use the
same test instant. Omit `clock` for real SQLite engine time and use a live Effect
clock. Provide your own `Crypto` Layer for deterministic entropy; the helper
never replaces cryptography. Advance/synchronize time only while auth operations
are idle; this helper does not prove independent-clock races or crash recovery.

Coverage is existing-account password sign-in and stateful session issuance,
verification, renewal, listing, revocation, and sign-out. Renewal invalidates the
previous credential, and retrying it fails. Sign-in remains non-idempotent.
Other strategies, password management, and other session modes are rejected with
`PersistenceConfigurationError` during acquisition. Direct unsupported password
management port calls fail with `PasswordUnavailable`. No registration, proof
delivery, MFA, identity-mutation, or OAuth services are supplied.

The [public-import consumer test](https://github.com/yielded-dev/auth/blob/main/examples/auth/test/in-memory.test.ts)
shows the complete composition, private credential collector, deterministic
entropy, expiry, renewal, sign-out, and isolation. Run it from a repository checkout:

```sh
vp -C examples/auth test test/in-memory.test.ts
```
