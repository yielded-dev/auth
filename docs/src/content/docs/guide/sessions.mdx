Configure sessions on `Auth.make`. Request-aware methods handle credential lookup
and delivery through the [HTTP boundary](./http-and-client).
For Electron and iOS, [browser sign-in](./browser-login) establishes a distinct
native session after hosted authentication and account confirmation.

## Configure sessions

```ts title="apps/server/auth.ts"
import { Schema } from "effect";
import { Auth, Sessions } from "@yielded/auth";

export const AppAuth = Auth.make("app/Auth", {
  claims: Schema.Struct({ displayName: Schema.String }),
  sessions: Sessions.stateful({
    idleTimeout: "30 minutes",
    maxAge: "7 days",
    renewAfter: "5 minutes",
  }),
});
```

This service only reads and manages sessions. Supply its bound
`AppAuth.sessions.StatefulSessionPersistence` and `SessionRepository` through your
storage Layer. It does not require authentication or provisioning authority.
Adding an authentication strategy also selects the default completion authority;
your account Layer supplies `AuthenticationAuthority` for issuing sessions.

Choose `Sessions.stateful()`, `Sessions.stateless()`, or `Sessions.stateAssisted()`.

| Mode           | Ordinary verification                                               | Revocation visibility                                 |
| -------------- | ------------------------------------------------------------------- | ----------------------------------------------------- |
| Stateful       | Authoritative persistence, or an explicitly enabled cookie snapshot | Immediate without caching; otherwise up to `cacheFor` |
| Stateless      | Signed session, without storage                                     | Until token expiry                                    |
| State-assisted | Signed session plus authoritative validity storage                  | Immediate                                             |

State-assisted sessions require a `SignedSessionValidity` service backed by the
same authority as identity changes. Signed claims remain snapshots; a validity
check does not refresh them or load application profile data.

Signed modes acquire their keys from `Sessions.SessionSigningKeys`. Supply the
service once, alongside your [crypto Layer](../reference/crypto#use-with-auth):

```ts title="apps/server/session-keys.ts"
import { Sessions } from "@yielded/auth";
import { Layer } from "effect";

import { sessionKeyring } from "./secrets";

export const SessionKeysLive = Layer.succeed(Sessions.SessionSigningKeys, sessionKeyring);
```

`sessionKeyring` has the `Sessions.SessionSigningKeyring` data shape: an
`activeKeyId` and `keys` with `id` and redacted base64url `material`. Each key needs
at least 32 random bytes. Provide `SessionKeysLive` to the Auth Layer; constructors
take policy options, not keys. Keep retired verification keys until their tokens
expire, and install key changes in every runtime.

Stateless sessions default to a fifteen-minute maximum age because sign-out
cannot revoke an issued token. Their
idle timeout and renewal interval are bounded by that lifetime. Stateful and
state-assisted sessions default to a thirty-day maximum age, seven-day idle
timeout, and renewal after one day. Explicit options select application policy;
shorter lifetimes bound the idle and renewal intervals.

Issuer and audience default to the stable session namespace, generation to `1`,
and the token limit to `4096` bytes. The shorter stateless default rejects older
tokens issued with a longer lifetime. Keep an explicit `maxAge` to retain that
policy, or set `maximumIssuedAge` to the previous limit until those tokens expire
while issuing new shorter-lived tokens.

### Cache ordinary session reads

Cookie caching is off by default. Opt in for opaque stateful sessions:

```ts
Sessions.stateful({ cacheFor: "5 minutes" });
```

`cacheFor` cannot exceed five minutes or `renewAfter`, whichever is shorter.
The window starts before the authoritative read, so storage or response delays
cannot extend it. Features with `requireImmediateInvalidation: true` reject this
configuration at startup; relax those feature policies only when accepting the
delay (TOTP defaults to `true`).

Provide `SessionSigningKeys` and HMAC support with your crypto Layer. A cache hit
verifies a signed public snapshot locally without a persistence lookup. The
snapshot is bound to the exact credential, session namespace and browser mutation
generation, and expires no later than the session. Cache signatures use a separate
purpose and derived key from signed sessions. The cookie is signed, not encrypted.

Cached claims may hide revocation, password changes, disablement, or authoritative
claim updates for up to `cacheFor`. This delay applies to ordinary `getSession()`
and `requireSession()` reads. Invalidation reports `existingSessions: "cache-expiry"`
with the configured `maximumExposureMillis`. Explicit verification, management,
step-up, and mutations always read authoritative state.

The HTTP boundary clears the snapshot and rotates a small HttpOnly generation
cookie on admitted mutations. Reads never write that generation: a delayed read
response cannot restore a usable snapshot after the mutation response arrives.
Without a valid generation or a cache response sink, reads use persistence. Lost
mutation responses, other clients, and replayed cookie pairs retain the fixed
`cacheFor` exposure bound.

Invalid or duplicate cache cookies are ignored. Oversized snapshots and cache
backend failures produce sanitized diagnostics and fall back to authoritative
reads. See [cookie limits and delivery](../reference/http#cookies-and-request-policy).
Signed session modes remain uncached, avoiding a second copy of their claims.

## Read the current session

Inside an existing Effect handler covered by `http.middleware`:

```ts
const auth = yield* AppAuth;
const session = yield* auth.getSession();
```

The method reads the incoming session credential from `Auth.AuthRequest`. Missing,
invalid, or expired credentials return `null`. An unavailable session store,
defect, or interruption remains a failure. No cookie parsing or catch handler is
needed in application code.

For a handler that requires authentication:

```ts
const auth = yield* AppAuth;
const session = yield* auth.requireSession();
```

An anonymous request fails with `AuthenticationRequired`. The
[HTTP guide](./http-and-client#protect-an-httpapi-group) shows how to require a
session for an entire HttpApi group.

To bypass the cookie snapshot:

```ts
const session = yield* auth.getSessionFresh();
```

Over HTTP, use `GET /auth/getSessionFresh`. The client exposes
`client.auth.getSessionFresh()` and the query atom `auth.freshSession`; see the
[client guide](./client#read-a-session-and-sign-out). A fresh read checks current
validity; it does not regenerate signed-token claims or load application profile
data automatically.

Outside a request, verify an explicit credential:

```ts
const auth = yield* AppAuth;
const session = yield* auth.verifySession(redactedCredential);
```

Explicit verification, management inspection, and step-up inspection always use
the authoritative strategy, bypassing the cookie cache.

## Sign out

In the same request context, call the service directly:

```ts
const auth = yield* AppAuth;
const result = yield* auth.signOut();
```

Sign-out reads the incoming credential without first verifying it and clears the
client credential and cached snapshot through private delivery. Its result reports `revoked`,
`already-invalid`, `client-only`, or `SessionSignOutUnavailable`. Local clearing
is not proof of server revocation; do not report global sign-out after a storage
failure. [Mounting the auth routes](./http-and-client#configure-the-server) supplies
request context and cookie delivery.

## Renew a session

```ts
const auth = yield* AppAuth;
const session = yield* auth.renewSession();
```

Renewal delivers a replacement credential through the request boundary.
`getSession()` and `requireSession()` do not rotate credentials.

## Custom completion and additional factors

Omit `sessions` from `Auth.make` when supplying custom session/completion Layers.
The lower-level `AppAuth.sessions.statefulLayer(policy)`, `statelessLayer(policy)`,
and `stateAssistedLayer(policy)` constructors remain available for runtime-selected
policy. Signed layers acquire `SessionSigningKeys` from their environment too.
Configure cookie caching through `Auth.make` with `Sessions.stateful({ cacheFor })`;
the cache implementation is private to that configured Auth Layer.

Configure `completionLayer({ pendingLifetimeMillis, attemptLimit })` with
`PendingAuthentication` persistence to support a second factor. A pending proof
is not an authenticated session. [TOTP](./totp) shows the complete Layer setup.

`SessionStrategy.inspect` returns private provenance for authorization decisions;
ordinary verification results omit it. Step-up binds its challenge to the source
session and credential revision and rechecks both before replacing the session.
