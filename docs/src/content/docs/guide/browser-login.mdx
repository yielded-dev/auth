`BrowserLogin` lets a native app use your existing hosted sign-in page. Your
server decides whether to reuse the browser session, confirm the account, or
require fresh authentication. The native host exchanges a short-lived code for
its own session. Browser cookies stay in the browser. Existing direct native
authentication remains available.

## Server and hosted page

Build the shared `BrowserLoginContract.make(namespace, Session, { basePath })`
from your session contract. On the server, bind the same namespace and path with
`BrowserLogin.make(AppAuth.sessions, { basePath })`.

```ts
import { BrowserLogin } from "@yielded/auth";

const login = BrowserLogin.make(AppAuth.sessions, { basePath: "/auth/browser-login" });
const LoginLive = login.layer({
  clients: [
    {
      clientId: "desktop",
      displayName: "Example Desktop",
      returnUrl: "com.example.desktop://auth/callback",
      browserSession: "confirm",
    },
  ],
});
```

Supply the existing session strategy, authentication authority, and
`BrowserLogin.Persistence`. The SQL companion's `BrowserLoginPersistence.layer`
supports SQLite, D1, and PostgreSQL; apply its `migration` through your migrations.
Use an exact registered HTTPS or reverse-domain custom-scheme return URL, without
query parameters or fragments. Attempts expire after two minutes by default;
`lifetimeMillis` accepts one second through five minutes.

Mount **`login.http`** with the existing `OperationHttpServer` configuration and
invocation Layers. This wrapper restricts description and authorization to the browser and
initiation, exchange, status, and cancellation to admitted native requests. Native
admission must reject cookies, browser-origin requests and unsupported clients;
application ingress limits still apply. A public client marker is not a secret.

The hosted page receives an `attempt` query parameter. Call `routes.describe`
with `{ attemptId }` for the registered app's `displayName`, `browserSession`
policy, and attempt expiry. Resolve this public operation as a guest even if an
expired browser cookie is present. App names and policy come from server
registration, never from query parameters.

| `browserSession` | Existing browser session                             | Return URL requirement                             |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------- |
| `automatic`      | Reuse an eligible session on initial page load.      | Claimed HTTPS with a signed Apple app association. |
| `confirm`        | Display the account and require “Continue to app”.   | Registered custom scheme or claimed HTTPS.         |
| `reauthenticate` | Require authentication at or after attempt creation. | Registered custom scheme or claimed HTTPS.         |

For `automatic`, compose a one-shot Effect Atom initializer that captures the
initial session, reads the description, and calls `routes.authorize` with
`{ attemptId, decision: "automatic", expectedSessionId: session.sessionId }`.
The server enforces the policy. Later session refreshes must not authorize again.
Custom schemes cannot enable automatic reuse: another app can claim the same
scheme, and PKCE alone does not establish the initiating app's identity.

For fresh authentication, make the action explicit, such as “Sign in and return
to app”. After login and MFA complete, compose authorization and callback
navigation in that same workflow, using
`{ attemptId, decision: "continue", expectedSessionId: result.session.sessionId }`.
No second confirmation is needed after this explicit action. A manual confirmation
uses the displayed session's ID. The [SQL example](https://github.com/yielded-dev/auth/tree/main/examples/persistence-sql)
shows these workflows and their lifetime ownership.

The server rejects a changed session, so a login in another tab cannot switch the
account being authorized. Its credential comes from the private browser cookie.
Keep the returned redacted `callbackUrl` in memory for a manual return link if
automatic navigation is blocked; do not repeat authorization to build that link.
Keep the page and redirect non-cacheable, with `Referrer-Policy: no-referrer`, and
exclude callback URLs from analytics.

Every policy requires original proofs that satisfy the application's current
authentication freshness policy. Stale proofs fail before approval; prompt the
user to sign in again. An uncompleted MFA flow cannot authorize the handoff.
The server retains private
authentication provenance and checks current subject/factor authority again when
issuing the native session; public account metadata supplies no authority.
Approval captures a short-lived grant: signing out that browser session afterward
does not withdraw it. Cancelling the attempt does. Exchange rechecks the current
client registration and reauthentication policy. An automatic approval also
requires the same registered Apple app identity and automatic policy at exchange.

## Claimed HTTPS callbacks

Use HTTPS callbacks when an existing browser session should return to the app
without confirmation. Register the signed app's application-identifier prefix
and bundle identifier with the exact return URL:

```ts
const clients: ReadonlyArray<BrowserLogin.Client> = [
  {
    clientId: "ios",
    displayName: "Example for iOS",
    returnUrl: "https://links.example.com/auth/callback",
    appleAppId: "ABCDE12345.com.example.app",
    browserSession: "automatic",
  },
];

const LoginLive = login.layer({ clients });
const association = BrowserLogin.appleAppSiteAssociation({
  clients,
  origin: "https://links.example.com",
});
```

Run `association` during deployment and serve its compact JSON result at
`https://links.example.com/.well-known/apple-app-site-association`, with
`Content-Type: application/json`, valid public HTTPS on port 443, and no redirects.
The helper generates both `webcredentials` and `applinks` entries from the same
registry and rejects an oversized document. It generates configuration; it does
not verify an installed app or deploy the file.

Sign the app with the matching Associated Domains entitlement: iOS authentication
sessions use `webcredentials:links.example.com`; macOS Universal Links use
`applinks:links.example.com`. The file and signed entitlement must both be in place
before enabling automatic reuse. Treat every app associated with the callback
host as a trusted receiver: iOS's `webcredentials` association is host-wide.
Use a separate callback host when app identities need separate trust boundaries.

Prefer a callback subdomain distinct from the hosted account page. Browser and
user routing choices can still require an “Open in app” action on macOS. If the
HTTPS destination opens in a browser, never forward its code to a custom scheme.
See Apple's [associated-domain setup](https://developer.apple.com/documentation/xcode/supporting-associated-domains)
and the platform adapter READMEs for signing and device verification.

## Native host

Provide `BrowserLogin.Browser`, `BrowserLogin.Vault`, `Crypto.Crypto`, and one
`OperationHttpClient.Client`. Configure the transport with the **same vault** as
its native credential store, cookie omission, redirect rejection, and no mutation
retries. Supply cryptography from the native platform; React Native does not imply
browser WebCrypto support.

`BrowserLogin.makeClient(contract, { clientId, returnUrl, hostedUrl, ephemeral })`
returns Effects for `signIn`, `resume`, `cancel`, and `status`, plus `finish(url)`
for host-delivered callbacks. Compose these in your Effect/Atom workflows.
React and Electron renderers receive public session state only. Use existing session
operations for protected API calls, restoration, and sign-out.

| Platform | Adapter                                   | Ownership                                                                                |
| -------- | ----------------------------------------- | ---------------------------------------------------------------------------------------- |
| Electron | `@yielded/auth-electron/BrowserLogin`     | Main-process browser launch, protocol events and platform-encrypted storage.             |
| iOS      | `@yielded/auth-react-native/BrowserLogin` | `ASWebAuthenticationSession` through Expo WebBrowser; Keychain through Expo SecureStore. |

The [Electron example](https://github.com/yielded-dev/auth/tree/main/examples/browser-login-electron)
and [SQL hosted account app](https://github.com/yielded-dev/auth/tree/main/examples/persistence-sql)
show full composition and account replacement. The
[iOS adapter setup](https://github.com/yielded-dev/auth/tree/main/packages/auth-react-native#browser-login)
covers native peers, Expo Modules setup, and callback registration. iOS requires
a native development build; a JavaScript-only preview cannot exercise the bridge.

On Electron, the main process owns a single-instance lock and scoped callback
listeners. Packaged protocol registration differs by operating system. HTTPS
callbacks require a signed, packaged macOS app and arrive through its native
Universal Link activity event. If launch
or registration fails, show a recoverable error and retain the attempt; never
fall back to an embedded login window or plaintext credential storage. Validate
both IPC sender and payload, and expose no credential-reading IPC method.

On iOS, normal sessions may share browser sign-in state. `ephemeral: true` requests
an isolated browser session; it does not sign out or erase Keychain data. Expo
WebBrowser supports custom-scheme callbacks and, on iOS 17.4+, HTTPS authentication
callbacks. Older iOS versions reject HTTPS; there is no custom-scheme fallback.
Interruption dismisses the prompt; late results are discarded. The SecureStore
vault keeps attempts and credentials together with device-only, unlocked Keychain
access and no biometric prompt. Keep one writer per service. Keychain data can
survive uninstalling the app.

## Lifetimes and recovery

The native session has a distinct identity and credential, with unchanged original
assurance, proof timestamps, and authentication time. Its initial expiry cannot
exceed the source session's expiry; its absolute lifetime cannot exceed the source
absolute expiry or current session policy. Renewal follows the configured strategy.
Signing out in one client leaves the other session intact. Subject-wide revocation
and account disablement retain the guarantees of your configured session mode.

Before account replacement, sign out the old native session. A successful exchange
clears previous pending credentials and advances the transport's response generation;
your Atom workflow must also publish the new subject and invalidate its queries.

Cancellation closes the platform prompt when its Effect is interrupted. Then call
`cancel` to retire a waiting attempt. Expired attempts cannot authorize or exchange.
After restart, `resume` can reopen a waiting hosted flow, or `finish` can consume a
validated cold-start callback. The app can always restore a securely saved session
through its protected session endpoint.

**An uncertain exchange is never retried.** The host durably records `Exchanging`
before sending it; the server durably consumes the attempt before issuing a session.
`status` reports `Exchanging` or `Complete`, with the issued session ID when known.
Restore and verify the saved credential, or revoke the possible session through
session management. If issuance has no known receipt, subject-wide revocation or
the session's bounded expiry resolves the possible orphan according to session
capabilities. Only after that deliberate reconciliation should the host call
`acknowledge` and start another attempt. A timeout, duplicate callback, or lost
credential-store response is not permission to issue again.

SQL storage rejects ambient transactions for these standalone commits. It can
delete expired attempt records, but an exchange may have committed without a
deliverable credential; cleanup does not revoke that session. This conservative
policy trades recovery convenience for preventing repeated issuance. Validate the
full browser return, platform storage and relaunch behavior in a packaged Electron
app and on a signed physical iOS device before claiming platform acceptance.
