`BrowserLogin` opens your hosted sign-in page in the system browser, then returns
to the native app with its own session. Browser cookies stay in the browser;
the app keeps its credential in a secure vault. Your server chooses whether an
existing browser session can be reused or needs confirmation or fresh sign-in.

## Register your app

```ts
import { BrowserLogin } from "@yielded/auth";

const clients: ReadonlyArray<BrowserLogin.Client> = [
  {
    clientId: "ios",
    displayName: "Example App",
    returnUrl: "https://links.example.com/auth/callback",
    appleAppId: "ABCDE12345.com.example.app",
    browserSession: "automatic",
  },
];

const login = BrowserLogin.make(AppAuth.sessions, { basePath: "/auth/browser-login" });
const LoginLive = login.layer({ clients });
```

Register the exact return URL, without query parameters or fragments. HTTPS
callbacks need the [app/domain association below](#claimed-https-callbacks).
For a custom scheme, use a URL such as `com.example.app://auth/callback`, omit
`appleAppId`, and choose `confirm` or `reauthenticate`.

| `browserSession` | When the browser is already signed in                                                    |
| ---------------- | ---------------------------------------------------------------------------------------- |
| `automatic`      | Reuse an eligible session and return immediately. Requires an associated HTTPS callback. |
| `confirm`        | Show the account and ask the user to continue.                                           |
| `reauthenticate` | Require authentication during this attempt.                                              |

All policies enforce your authentication freshness and MFA requirements. After
an explicit fresh sign-in, the page can return without a second confirmation.

Provide your session services and `BrowserLogin.Persistence`, then mount
**`login.http`** with `OperationHttpServer`. This keeps browser and native
requests separated. Share `BrowserLoginContract.make(namespace, Session, { basePath })`
with the clients, using the same session namespace and route path.

The [SQL account example](https://github.com/yielded-dev/auth/tree/main/examples/persistence-sql)
shows the complete server and hosted-page setup. Its `BrowserLoginPersistence.layer`
supports SQLite, D1, and PostgreSQL; apply the supplied migration through your
application's migrations. Attempts expire after two minutes by default.

## Connect the hosted page

The page receives an `attempt` query parameter. Call `routes.describe` with
`{ attemptId }` through the operation client to get the registered app name and
policy. Keep this guest-readable even when an expired browser cookie is present.

Compose sign-in and return navigation in an Effect Atom workflow. Send
`routes.authorize` the following payload:

```ts
{ attemptId, decision: "continue", expectedSessionId: session.sessionId }
```

Use the session from the completed sign-in, or the account shown for manual
confirmation. For `automatic`, capture the initial browser session once and use
`decision: "automatic"`; later session refreshes must not trigger another approval.
The [hosted example](https://github.com/yielded-dev/auth/blob/main/examples/persistence-sql/src/browser-login-banner.tsx)
shows these workflows.

Navigate to the returned `callbackUrl`. Keep it in memory for a manual return link
if navigation is blocked; reuse that link rather than authorizing again. Use
`Cache-Control: no-store` and `Referrer-Policy: no-referrer`, and keep callback URLs
out of logs and analytics.

## Claimed HTTPS callbacks

Use the signed app's application-identifier prefix and bundle ID for `appleAppId`.
Generate Apple's association document from the same client registration:

```ts
const association = BrowserLogin.appleAppSiteAssociation({
  clients,
  origin: "https://links.example.com",
});
```

Run this Effect and serve the resulting compact JSON at
`https://links.example.com/.well-known/apple-app-site-association`, over public
HTTPS on port 443 with `Content-Type: application/json` and no redirects.

Sign the app with the matching Associated Domains entitlement:

- **iOS 17.4+:** `webcredentials:links.example.com` for authentication sessions.
- **Packaged macOS Electron:** `applinks:links.example.com` for Universal Links.

Both the hosted file and signed entitlement must be deployed before enabling
`automatic`. Treat every app associated with that host as a trusted receiver;
use separate callback hosts when apps need separate trust boundaries.

Prefer a callback host distinct from the login page. Browser settings may still
require an “Open in app” action on macOS. Never forward an HTTPS callback's code
to a custom scheme. See [Apple's setup guide](https://developer.apple.com/documentation/xcode/supporting-associated-domains)
and the platform adapters below.

## Native host

Create the client with
`BrowserLogin.makeClient(contract, { clientId, returnUrl, hostedUrl })` and call
its `signIn` Effect. Provide `BrowserLogin.Browser`, `BrowserLogin.Vault`,
`Crypto.Crypto`, and `OperationHttpClient.Client`. The HTTP client must use the
same vault, omit cookies, reject redirects, and avoid retrying mutations.

| Platform | Setup                                                                                                                                                                                               |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Electron | [Main-process adapter](https://github.com/yielded-dev/auth/tree/main/packages/auth-electron) and [runnable example](https://github.com/yielded-dev/auth/tree/main/examples/browser-login-electron). |
| iOS      | [React Native adapter](https://github.com/yielded-dev/auth/tree/main/packages/auth-react-native#browser-login), using Expo WebBrowser and SecureStore. Requires a native build.                     |

Keep credentials in the native host; expose only public session state to React
or Electron renderers. On iOS, `ephemeral: true` requests a browser session without
shared browsing data. Electron does not support that option.

## Lifetimes and recovery

Browser and native sessions are separate: signing out of one leaves the other
signed in. The native session inherits the source's authentication and lifetime
limits. Sign out the old native session before switching accounts.

After restart, restore the saved session or use `resume` for a waiting login.
Use `finish(url)` for host-delivered callbacks. To cancel, interrupt any active
sign-in first, then call `cancel` to retire the attempt.

**Do not retry an uncertain exchange or clear its vault to start again.** Recover
and verify the saved session only if it matches the completion receipt from `status`.
Otherwise, revoke the possibly issued session or wait for its absolute expiry.
Only after that reconciliation should you call `acknowledge` to allow another
attempt. The login attempt's expiry does not expire a session it may have issued.
